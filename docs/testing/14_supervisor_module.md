# Supervisor Management & Monitoring — Test Cases

## Overview

This module covers the Supervisor role's own administrative and monitoring surface: profile CRUD for supervisor staff accounts (`SupervisorController`), cluster-scope assignment of supervisors (`SupervisorAssignmentController`), read-only monitoring of the collectors under a supervisor's supervision (`SupervisorCollectorController`, `SupervisorMonitoringController`), arrears/tunggakan analysis per cluster (`SupervisorTunggakanController`), live collector-location monitoring (`SupervisorMapController`), the supervisor notification/escalation inbox (`SupervisorNotificationController`), WhatsApp/in-app broadcasts to collectors and residents (`BroadcastController`), and asynchronous collector-performance report exports (`SupervisorReportController`). Approval decision workflows (installment plans, billing adjustments, reversals, penalty waivers) reached via `/supervisor/approvals` are covered in `10_approvals_reversals.md`, and the aggregate `SupervisorDashboardController` KPI page is covered in `04_dashboard.md` — both are referenced here only for navigation context, not duplicated. On Web Admin, the Supervisor role uses dedicated pages under `/supervisor/*` (plus admin-only CRUD pages under `/admin/supervisors/*`); on Android, Supervisor uses the same app as residents/collectors but is routed into a distinct `SupervisorHomeShell` after login. All cases test **current, confirmed behavior only**; where the research could not fully confirm a rule or a UI surface (e.g. whether a Web detail view exists for a given endpoint, or whether a gap is an intentional design choice), a `> Note:` callout flags the ambiguity instead of inventing an expected behavior. This file also contains a dedicated, explicitly-flagged test (TC-SUP-108) for a possible collector-scope data leak in the payments monitoring endpoint — phrased neutrally as "verify observed behavior" for the QA lead's review, not asserted as a confirmed defect.

### 1. Supervisor Profile Management (CRUD)

`GET/POST supervisors`, `GET/PUT/DELETE supervisors/{id}`, `PATCH supervisors/{id}/status`, `GET supervisors/{id}/activity-history`, `POST supervisors/{id}/photo` — permissions `supervisor.view/create/detail/update/delete/activate` respectively. Validation mirrors `CollectorController` exactly (same field set minus `working_area_notes`/`initial_monthly_target`, same auto-generated `SPV-0001`-style code, same `account_status`/`employment_status` enums). A caller who themselves holds the `supervisor` role may only view their own record via `show()` (403 otherwise); any other role may view any supervisor. This is a Web Admin (`SupervisorsPage`, `SupervisorDetailPage`) + Backend API surface only — no Android screen manages other supervisors' profiles (a supervisor's own profile is shown read-only via a bottom-sheet sourced from `auth/me`, not from this controller).

> Note: `SupervisorController::show()`'s `unread_notifications` figure counts ALL unread notifications system-wide with no per-supervisor scoping — unlike every other supervisor-monitoring endpoint, and unlike the equivalent figure on the Supervisor Dashboard. TC-SUP-027 tests this directly. Similarly, `pending_approvals` here excludes null-`related_collector_id` approvals while the Dashboard's equivalent figure includes them (TC-SUP-028).
> Note: Whether deleting a supervisor who still has active `SupervisorAssignment` rows succeeds or throws a database integrity error (TC-SUP-037) was not independently confirmed for this controller — it is inferred only from the confirmed equivalent restriction on `collector_assignments.collector_id`. Treat as a behavior to observe and report, not an assumed outcome.

### 2. Supervisor Assignments (Cluster Scope)

`GET/POST supervisor-assignments`, `PUT/DELETE supervisor-assignments/{id}`, `POST supervisor-assignments/{id}/reassign` — mirrors `CollectorAssignmentController` but with a single, always-required scope type (cluster only, no block/unit/resident variants). `create`, `update`, and `delete` all share the SAME permission (`supervisor-assignments.assign` — there is no distinct delete permission, unlike collector assignments). `reassign` requires `supervisor-assignments.reassign`. Duplicate-active-scope guard is keyed on `(supervisor_id, cluster_id)` plus date-range overlap. Web Admin only (`SupervisorAssignmentsPage`) — no Android admin screen for this.

> Note: The exact validation-error message text for the duplicate-overlapping-scope rejection was confirmed verbatim only for the collector-assignment equivalent (which references "kolektor" wording); the supervisor-assignment guard is described in the research as "identical logic" but its exact message string was not independently re-confirmed, so expected results below describe the validation outcome generically rather than quoting an unconfirmed literal string.

### 8. Broadcast (WhatsApp / Announcement)

Types: `collector` (scoped to `SupervisorAssignmentService::collectorIdsFor`, optionally further intersected by `cluster_id`), `resident` (targets units/residents, `unit_ids` wins over `cluster_id` if both given, NO supervisor-scope restriction), `announcement` (always broadcasts to the full in-scope collector set, ignores all filter params, delivered in-app only — never via WhatsApp).

> Note: `WhatsAppBroadcastService` is a genuine Fonnte HTTP integration, not a stub — but if `FONNTE_TOKEN` is unset (the default in most dev/test environments), every non-announcement recipient is recorded as delivery_status=failed with provider_response=provider_not_configured, and the broadcast still returns 201.
