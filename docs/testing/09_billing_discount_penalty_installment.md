# Billing, Discount, Penalty & Installments — Test Cases

## Overview

This module covers the core money-generation and money-adjustment surface of Duta Residence: `BillingController` (monthly/special/back-dated invoice generation, the approve/approve-batch workflow, manual per-billing discount, the aggregate summary, and the filterable billing list — all under `api/v1/billings*`), `DiscountRuleController` (the reusable auto-discount rules consumed at billing-creation time, `api/v1/discount-rules*`), `PenaltyRuleController` plus the global `PenaltySetting` admin toggle (`api/v1/penalty-rules*`, `api/v1/admin/settings/penalty`), `PenaltyWaiverController`'s **submission and listing** endpoints only (`billings.waive-penalty` / `billings.view` — the waiver's **approve/reject** decision is a dedicated endpoint fully covered in `10_approvals_reversals.md`), and the flat cash-ledger `InstallmentController` (`api/v1/installments*`, `api/v1/units/{unit}/installments`) together with `BackPaymentController` (`api/v1/back-payments/process`). The approval-gated `InstallmentPlan` (submitted via `POST approval-requests/installment-plans` and decided via the generic Approval Center) is a **separate** model from the `Installment` record tested here and is also fully covered in `10_approvals_reversals.md` — per the research, approving an `InstallmentPlan` never creates or links any `Installment` row, so the two are tested independently by design, not by omission.

Platform coverage is uneven across this module and every gap below is a confirmed research finding, not an assumption: the Web Admin `BillingsPage` (`/billings`) and `InstallmentsPage` (`/installments`) give full UI coverage to `billings.*` and to creating/listing `Installment` records, so those test cases are written primarily against Web Admin with Backend-API-level validation/boundary variants. By contrast, the research found **no Web Admin page, no route, and no Android screen** for managing `DiscountRule`s, managing `PenaltyRule`s, viewing/updating the global `admin/settings/penalty` toggle, or submitting a `PenaltyWaiver` (the Supervisor Approvals inbox only *decides* waivers already submitted elsewhere) or calling `back-payments/process` directly (the mobile collector's own "Proses Bayar" screen calls the general `payments/process` endpoint, never the back-payment-specific one). Every test case touching those five surfaces is therefore written at the Backend API level with a `> Note:` callout flagging the missing UI for the QA lead to confirm with product/dev — it may be an intentional API/seeder-only admin surface, or a genuinely missing screen.

Finally, the current `PenaltyService` calculation is confirmed **tier-based** (a flat per-tier amount resolved by matching `overdue_months` into a rule's `[minimum_overdue_month, maximum_overdue_month]` range), **not** an accumulating/running-balance model. All penalty-formula test cases in this document target this CONFIRMED current behavior; if any roadmap document assumes a running-balance redesign, that redesign is not present in the code the research examined, and the boundary tests below should be read as documenting current behavior, not endorsing it as final.

### Prepare Monthly Billing (`billings.prepare`)

`POST billings/prepare-monthly` — validates `{year: required, integer, min:2020, max:2100}`, `{month: required, integer, between:1,12}`. `BillingService::prepareMonthly()` loops every `Unit` with `status_id='AK'` (active), resolves that unit's cluster rate for the period, computes any auto-discount, and calls `Billing::firstOrCreate(['unit_id','year','month'], [...])` — this specific action is duplicate-safe by design (see the dedicated Duplicate-Billing Prevention section for the contrast against `prepare-special`/`prepare-back`, which are NOT duplicate-safe).

### Prepare Back-Dated Billing (`billings.prepare-back`)

`POST billings/prepare-back` — validates `{unit_id: required, exists:units}`, `{periods: required, array, min:1}`, `{periods.*.year: required, integer, min:2020, max:2100}`, `{periods.*.month: required, integer, between:1,12}`, `{periods.*.amount: required, numeric, min:0}`. ### Duplicate-Billing Prevention

The `billings` table has a hard database unique constraint on `(unit_id, year, month)`, independent of `billing_type`. `prepare-monthly` is duplicate-safe by design (`firstOrCreate`). `prepare-special` and `prepare-back` are **NOT** duplicate-safe — they call `Billing::create()` directly, so a second call for a unit/period that already has ANY billing (regardless of whether the first one was regular/special/back) throws an uncaught `QueryException`, surfacing as a bare 500 ("Terjadi kesalahan server.") instead of a clean 422. `prepare-back` additionally loops its periods without a wrapping database transaction at the controller level, so a mid-batch collision leaves earlier periods in the same request already committed.

> Note: This is flagged in the research as the single highest-value duplicate-prevention gap in the whole billing engine — QA should treat any of the 500-response cases below as confirmed current behavior worth escalating to engineering as a hardening candidate (e.g. wrapping in a transaction and/or pre-checking with a friendly 422), not as a false positive in this test suite.

### Approve Billing (Single) (`billings.approve`)

## Discount Rules (DISC)

`DiscountRuleController` (`permission:discount-config.*`) manages reusable `DiscountRule` records consumed automatically at billing-creation time via `DiscountService::calculateForNewBilling()`. There is only ONE discount slot per billing (`billings.discount`) — a rule never "stacks" additively with another rule or with a later manual override; whichever discount is applied most recently always REPLACES the prior value.

> Note: The research found no Web Admin route, page, or Android screen for managing `DiscountRule`s — the `discountRules` API domain exists in the frontend's API client layer, but no page in the routing table (`AppRoutes.jsx`) or page-by-page inventory calls it. All test cases below are written at the Backend API level; confirm with product/dev whether this is an intentional API/seeder-only surface or a missing admin screen.

## Penalty Rules & Waivers (PEN)

`PenaltyRuleController` (`permission:penalty-config.*`) manages tier-based `PenaltyRule` rows consumed by `PenaltyService::calculatePenalty()`; the global `PenaltySetting` (`admin/settings/penalty`) toggles whether penalties apply at all and the payment-allocation order; `PenaltyWaiverController`'s submission and listing endpoints let staff request/browse penalty relief on a specific billing (the approve/reject decision is covered in `10_approvals_reversals.md`).

> Note: The research found no Web Admin route/page and no Android screen for managing `PenaltyRule`s, viewing/updating the global `admin/settings/penalty` toggle, or submitting a `PenaltyWaiver` — the Supervisor Approvals inbox (`/supervisor/approvals`) only ever *decides* waivers, it has no "create waiver" form (per the research: "reversal/penalty_waiver requests presumably originate elsewhere and only get decided here"). All test cases for these three surfaces are written at the Backend API level; confirm with product/dev whether this is an intentional gap.

### Penalty Accumulation Formula — Business Rule Boundary Tests

Confirms the current, CONFIRMED behavior of `PenaltyService::calculatePenalty()`: `overdue_months = max(0, (now.year-billing.year)*12 + (now.month-billing.month))` — **month-granularity, not day-granularity** — resolved into a matching `PenaltyRule`'s flat `penalty_amount` for that tier, minus cumulative `penalty_waived_amount`, floored at 0. Moving from one tier to the next REPLACES the amount; it is NOT an accumulating running balance that adds up month over month. Once a billing `isPaid()`, its penalty is FROZEN to the last computed value and never recalculates again; once `isCancelled()`, penalty is always 0.

> Note: If any roadmap document describes penalty as a "running/accumulating balance" design, that design is NOT what the current `PenaltyService` code implements — every case below documents the CONFIRMED tier-based/flat-replacement behavior. Flag any discrepancy against a running-balance expectation to product/dev rather than treating these results as bugs.

## Installments & Back-Payments (INST)

`InstallmentController` (`permission:installments.*`) manages the flat, free-text `Installment` cash-ledger record — confirmed to be purely informational: creating one does NOT touch any `Billing`'s `principal_paid`/`penalty_paid`, does NOT create a `PaymentTransaction`, and does NOT link to an `InstallmentPlan` (the `installment_plan_id` column exists on the table/model but no code path anywhere ever sets it). There is no update or delete endpoint for `Installment` at all — once created, a record can never be edited or removed via the API. `BackPaymentController`'s `back-payments/process` is confirmed to be a thin wrapper around the exact same `PaymentService::process()` used by the regular loket payment flow, differing only in that it never accepts an `amount` field (always a full settlement of the selected billings) and returns a distinct success message.

> Note: The research confirmed the Web Admin `InstallmentsPage` (`/installments`) covers creating and listing `Installment` records via the general `unit_id`-filtered list, but found no confirmed UI (Web Admin or Android) calling the nested `GET units/{unit}/installments` endpoint specifically, nor any UI anywhere calling `POST back-payments/process` — the mobile collector's own "Proses Bayar" screen (`payment_collection_screen.dart`) calls the general `payments/process` endpoint instead. The by-unit listing and the back-payment cases below are written at the Backend API level; confirm with product/dev whether a dedicated back-payment UI is planned.

### Process a Back-Payment — Arrears Settlement (`payments.process`)

`POST back-payments/process` — `{unit_id: required, exists:units}`, `{billing_ids: required, array, min:1}`, `{billing_ids.*: integer, exists:billings}`, `{payment_method_id: required, exists:payment_methods}`, `{loket_code: nullable, string, max:20}`, `{cashier_name: nullable, string, max:50}`.
