# Payment & Payment Gateway — Black-Box QA Test Cases

This document covers Billing settlement via `PaymentController` (loket/cash counter search → preview → process, receipts list/detail), `PaymentGatewayController` (gateway transaction create/list/detail, staff-assisted manual-proof upload, verify/reject, the unauthenticated Xendit and Midtrans webhook endpoints), `PaymentGatewaySettingController` (settings show/update/test-connection), and the resident-portal payment slice of `ResidentPortalController` (payment-config, create-payment-on-invoice, own payment list/detail/receipt-download, own manual-proof upload) — on Web Admin, Web Resident Portal, Android App (Collector role for loket-equivalent field collection, Resident role for self-service), and Backend API (webhooks, and any scenario the discovered UI has no control for). Collector in-field cash/transfer collection (`payment_collection_screen.dart`) reuses the exact same `payments/search`, `payments/preview`, `payments/process` endpoints as the Web Admin loket workflow, so it is tested here as an Android App platform variant rather than a separate module. `BackPaymentController` ("pelunasan tunggakan lama") is a thin wrapper around the identical `PaymentService::process()` used by loket payments with no distinct business rule of its own, and `InstallmentController`'s free-text ledger ("Cicilan") never touches Billing/PaymentTransaction state at all — both are out of scope for this file.

> **Note on partial-payment testing via the UI:** neither the Web Admin "Proses Bayar Loket" form nor the Android "Proses Pembayaran" screen exposes an editable `amount` field — both always call `POST payments/process` without `amount`, which defaults to full settlement of every selected billing. The backend API itself does accept a nullable `amount` for partial payment. Because no discovered UI path can trigger a partial payment, the partial-payment-specific test cases below target the API directly (Platform: Backend API) rather than a UI platform, and should be re-verified against the UI once/if a partial-payment control is added.

> **Note on webhook duplicate-delivery signature bypass:** per the research, the `PaymentWebhookEvent::firstOrCreate` duplicate check runs strictly *before* `verifyWebhook()` is ever called. This means a request carrying an `event_id`/`order_id` that already exists with `status: 'processed'` short-circuits to `{duplicate: true}` 200 **without any signature/token check being performed on that replay at all** — even a replay with a deliberately wrong signature. This is tested below as current observed behavior, not a confirmed intended design.
